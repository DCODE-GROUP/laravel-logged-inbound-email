## Problem Statement

Today, this package (forked as `dcodegroup/laravel-logged-inbound-email`) verifies an inbound email webhook, builds an `InboundMessage` DTO, and hands it off to the consuming application's own queued job — nothing is ever recorded by the package itself. If that job fails, is misconfigured, or a webhook body turns out to be malformed after signature verification passes, there is no durable trace that the email was ever received. Application developers building on this package have no built-in way to see a history of inbound emails, inspect what a provider actually sent, track whether a given email has been processed yet, or link a received email back to the business records it created — they'd have to build all of that persistence and lifecycle tracking themselves, which is exactly the kind of undifferentiated work this fork exists to remove.

## Solution

The package durably records every inbound email that passes webhook verification as an `InboundEmail` Eloquent model, combining what a raw webhook receipt looks like with the parsed, normalized email fields, in a single row per webhook. That row tracks its own processing lifecycle (`Pending` → `Receiving` → `Received`, then `Processing` → `Processed`/`Failed`, driven partly by the package and partly by the consuming app's own job), stores attachments on a configurable disk via a companion `InboundEmailAttachment` model, and exposes two nullable polymorphic relations (`contactable`, `processable`) so the app can link the email to whatever business records it represents or produces. Persistence is mandatory and automatic — there is no config flag to disable it, since durable logging is this fork's entire reason for existing. The existing `InboundMessage` DTO and job-dispatch mechanism are unchanged; the app's job continues to receive the same serialized payload it does today, with the addition that it can now also load the corresponding `InboundEmail` row to update its status and attach relations.

## User Stories

1. As a package-consuming developer, I want every inbound email that passes webhook verification to be persisted automatically, so that I don't have to write my own persistence layer to get an audit trail.
2. As a package-consuming developer, I want the raw webhook payload preserved verbatim on the `InboundEmail` row, so that I can debug provider-specific quirks without needing to have captured the original request myself.
3. As a package-consuming developer, I want the parsed email fields (`from`, `to`, `reply_to`, `subject`, `html_content`, `text_content`, `message_id`, `received_at`, `provider`) available as normalized columns, so that I can query and filter inbound emails without parsing the raw payload myself.
4. As a package-consuming developer, I want attachments extracted to their own `InboundEmailAttachment` records backed by a configurable filesystem disk, so that large binary content doesn't bloat the `inbound_emails` table and I can control where files are stored.
5. As a package-consuming developer, I want to configure which disk attachments are written to via a single package-wide config value, so that I can point attachment storage at S3, a local disk, or wherever else fits my app's infrastructure.
6. As a package-consuming developer, I want the `InboundEmail` row's status to reflect whether the package successfully verified and parsed the webhook, so that I can distinguish "received cleanly" from "something went wrong before my job even ran."
7. As a package-consuming developer, I want an `error` column populated when parsing fails after verification succeeds, so that I can see why a specific inbound email never made it to `Received` without digging through logs.
8. As a job author in the consuming app, I want to call `markProcessing()`, `markProcessed()`, and `markFailed()` on the `InboundEmail` model from my own queued job, so that I can extend the same status lifecycle to cover my own business processing, not just the package's parsing step.
9. As a job author in the consuming app, I want to load the `InboundEmail` row that corresponds to the `InboundMessage` payload my job already receives, so that I can update its status and relations without the package needing to know about my job's internals.
10. As a package-consuming developer, I want a nullable `contactable` polymorphic relation on `InboundEmail`, so that I can link a received email to whichever of my own models represents "who this came from" (a Contact, a Customer, etc.), in whatever shape makes sense for my app.
11. As a package-consuming developer, I want a nullable `processable` polymorphic relation on `InboundEmail`, so that I can link a received email to whatever business record it produced (an Order, a Job, a Ticket, etc.).
12. As a package-consuming developer, I want a nullable `organization_alias` column automatically captured from the `{orgAlias}` route segment when multi-tenant routing is enabled, so that I can filter inbound emails per tenant without extra wiring.
13. As a package-consuming developer, I want a nullable `tenant_id` column that I populate myself, resolved against a single model class I declare in config (`tenant_model`), so that I can attach a real tenant relationship without the package needing to know my tenancy model's shape.
14. As a security-conscious developer, I want webhook requests that fail signature or tenant-policy verification to never be persisted at all, so that unauthenticated or malicious traffic doesn't pollute my inbound email history or become an unbounded storage/DoS vector.
15. As a package-consuming developer, I want provider control messages that aren't actually emails (e.g. an SNS `SubscriptionConfirmation`) to not create an `InboundEmail` row, so that my inbound email history only contains genuine attempted emails.
16. As a package-consuming developer, I want `InboundEmail` and `InboundEmailAttachment` to use soft deletes, with attachments cascading when their parent is soft-deleted, so that I retain an audit trail by default while still being able to prune old records deliberately.
17. As a package-consuming developer, I want the migrations for `inbound_emails` and `inbound_email_attachments` published as stub files into my app (consistent with how `config/inbound-email.php` is already published), so that I can customize columns, indexes, or the `tenant_id` foreign key type before running them.
18. As a package maintainer, I want the service provider rebuilt on `spatie/laravel-package-tools`'s `PackageServiceProvider`, so that config, migration, and future asset publishing follow a well-understood convention rather than hand-rolled `publishes()` calls.
19. As a package maintainer, I want the wider project restructured to match `spatie/package-skeleton-laravel` conventions (Testbench `workbench/`, its CI shape, `CHANGELOG.md`), so that the package looks and behaves like any other package in the Laravel ecosystem to future contributors.
20. As a package-consuming developer upgrading from the unforked upstream package, I want the composer package name and PHP namespace changed to `dcodegroup/laravel-logged-inbound-email` / `Dcodegroup\LaravelLoggedInboundEmail`, so that it's unambiguous this fork behaves differently (mandatory persistence) from the original.
21. As a package-consuming developer, I want existing behavior (route registration, provider verification, job dispatch, the `InboundMessage` DTO shape) to remain unchanged aside from the new persistence step, so that upgrading doesn't require me to rewrite my own job.

## Implementation Decisions

- **New model `InboundEmail`** (single table `inbound_emails`), combining what the `trady` reference project splits into a generic `Webhook` model and a separate `InboundEmail` model. Columns:
  - `payload` (json/text) — the raw webhook body exactly as received, unmodified.
  - Normalized parsed columns: `provider`, `from`, `to`, `cc`, `bcc`, `reply_to`, `subject`, `text_content`, `html_content`, `message_id` (for dedup reference, not enforced unique at v1 since retries aren't in scope), `received_at`.
  - `organization_alias` (nullable string) — captured automatically from the `{orgAlias}` route segment when `organization_in_route` is enabled; `null` otherwise.
  - `tenant_id` (nullable, unsigned big integer) — never populated by the package; set later by the consuming app against the model class declared in the new `inbound-email.tenant_model` config key.
  - `status` (string, backed by new `InboundEmailStatus` enum) and `error` (nullable text).
  - `contactable_id`/`contactable_type` and `processable_id`/`processable_type` — nullable morph columns, package never populates them.
  - Soft deletes (`deleted_at`).
- **New enum `InboundEmailStatus`**: `Pending`, `Receiving`, `Received`, `Processing`, `Processed`, `Failed`. The package itself only ever sets `Pending` (row created, right after webhook verification passes, before parsing begins), `Receiving` (parsing in progress), `Received` (an `InboundMessage` was successfully built) — or `Failed` with an `error` message if parsing throws after verification succeeded. `Processing`/`Processed`, and any app-driven `Failed`, are set exclusively by the consuming app calling `markProcessing()`/`markProcessed()`/`markFailed()` on the model — the package never calls these itself. One row is created per webhook and updated in place through its lifecycle; there is never more than one row per received webhook.
- **Verification failures are never persisted.** No `InboundEmail` row is created until after `InboundWebhookTenantPolicy::assertInboundAllowed()` and the provider handler's `verify()` both succeed. This is unchanged from current behavior — these still throw HTTP exceptions with nothing written to the database.
- **Non-email control messages produce no row.** When a provider handler's `toInboundMessage()` legitimately returns `null` for a message that was never an email in the first place (e.g. SES/SNS `SubscriptionConfirmation`/`UnsubscribeConfirmation`), no `InboundEmail` row is created — this is distinct from a parsing failure, which does create a `Failed` row.
- **New collaborator** responsible for the record/transition logic (naming TBD during implementation, e.g. `InboundEmailRecorder`), invoked from `InboundWebhookController::handleInbound()`: creates the `Pending` row right after `verify()` succeeds and before `toInboundMessage()` is called, flips it to `Receiving` around the parse call, and to `Received` with normalized columns once the `InboundMessage` is built — or to `Failed` with the caught exception's message if parsing throws. The controller's existing flow (tenant policy → provider config merge → handler resolution → verify → parse → dispatch → `200 OK` response) is otherwise unchanged.
- **New model `InboundEmailAttachment`** (table `inbound_email_attachments`), one row per attachment: `inbound_email_id` (foreign key, cascades on parent hard delete, cascades on parent soft delete via a model event), `filename`, `disk`, `path`, `content_type`, `size`. Attachment content from `InboundMessage::attachments` (currently base64-in-memory) is written to the disk named in the new `inbound-email.attachments.disk` config value at the point the `InboundEmail` row transitions to `Received`; the `InboundEmail.payload` column retains the full raw webhook body as-is (including any embedded attachment content the provider sent), while normalized/extracted attachment content lives only on disk — no separate stripping step needed since `payload` is the untouched original body, not a copy of `InboundMessage`.
- **New config keys** in `config/inbound-email.php`: `tenant_model` (nullable FQCN string, default `null`) and `attachments.disk` (string, single package-wide value, default to the app's default filesystem disk).
- **Service provider rewritten** to extend `Spatie\LaravelPackageTools\PackageServiceProvider`, using `configurePackage()` for config-file and migration-stub publishing; the existing dynamic route-prefix/middleware registration logic is retained by overriding `packageBooted()` (or equivalent) rather than relying on package-tools' static route loading, since the prefix and middleware are runtime-configurable.
- **Migrations published as stubs** (`vendor:publish --tag=laravel-logged-inbound-email-migrations` or package-tools' equivalent generated tag), matching the existing config-publishing pattern — not auto-run via `loadMigrationsFrom`.
- **New dependencies**: `illuminate/database` (for Eloquent/migrations, not currently required), `spatie/laravel-package-tools`.
- **Package identity change**: composer package renamed to `dcodegroup/laravel-logged-inbound-email`; PHP namespace changed from `Touqeershafi\LaravelInboundEmail` to `Dcodegroup\LaravelLoggedInboundEmail` across all source, config, routes, and tests.
- **Project restructuring** to follow `spatie/package-skeleton-laravel` conventions: Testbench `workbench/` app for local development, the skeleton's GitHub Actions workflow shape, and a `CHANGELOG.md`. Existing CI checks (Pint, PHPStan, PHPUnit) are preserved, just reshaped to the skeleton's script/workflow conventions.
- **`InboundMessage` DTO is unchanged** — it remains a transient, non-persisted value object. The job dispatch contract (`ProcessesInboundEmail`, `array $message` payload, optional `$orgAlias`) is unchanged; apps upgrade by optionally loading the `InboundEmail` row inside their existing job to call the new status methods and set relations, but nothing requires them to change their job's constructor or existing logic.

## Testing Decisions

- Good tests here assert **observable outcomes** — HTTP response status, dispatched jobs, and database/filesystem state — never internal method calls on the recorder collaborator or handler classes. This matches the existing test style in `tests/Feature/*InboundWebhookTest.php`, which already asserts `assertForbidden()`/`assertOk()` and `Bus::assertDispatched()`/`Bus::assertNothingDispatched()` rather than mocking internals.
- **Primary seam — existing Feature webhook tests**, extended per provider test file:
  - Verification-failure tests (already present, e.g. `test_rejects_invalid_signature`) gain an added assertion that `InboundEmail::count()` is `0` — confirming the "never persisted" decision holds.
  - Successful-dispatch tests (already present, e.g. `test_dispatches_job_with_normalized_payload`) gain assertions that exactly one `InboundEmail` row exists with `status === Received`, the raw `payload` matches what was posted, and normalized columns match the parsed `InboundMessage` fields.
  - New test per provider (or a shared case, given the parsing logic differs per handler) exercising a post-verification parse failure — e.g. SES with a validly-signed SNS envelope but malformed inner JSON (`SesInboundWebhookTest`, using the existing `BadRequestHttpException` path in `SesSnsHandler::toInboundMessage()`) — asserting the row lands at `status === Failed` with a non-empty `error`.
  - New test confirming an SNS `SubscriptionConfirmation` (valid signature, legitimately non-email) creates no `InboundEmail` row.
  - New test asserting attachments produce `InboundEmailAttachment` rows and files written to `Storage::fake()`, using an existing attachment-bearing fixture (Mailgun's `attachment-{n}` file upload path already has test coverage groundwork via `parseAttachments()`).
- **Secondary seam — new `tests/Unit/Models/InboundEmailTest.php`**, covering `markProcessing()`/`markProcessed()`/`markFailed()` transitions directly against the model (using a factory), since no HTTP path within this package calls these — they exist purely for the consuming app's job to call. Also covers the soft-delete cascade from `InboundEmail` to its `InboundEmailAttachment` rows.
- **`InboundRoutesTest`** (route registration) is the regression seam for the service-provider rewrite — it must keep passing unchanged after the switch to `PackageServiceProvider`, confirming the prefix/middleware/route-group behavior wasn't altered by the rewrite.
- No new test seams beyond these two; handler-level unit tests are not introduced since handler behavior is already fully exercised through the Feature/HTTP seam.

## Out of Scope

- Message-ID-based deduplication of retried webhooks (a `message_id` column exists for future use, but no uniqueness constraint or existing-row lookup is implemented in this pass).
- Any resolver/contract for automatically populating `tenant_id` from `organization_alias` — it stays a plain nullable column the app sets itself.
- A morph-style (`tenant_id`/`tenant_type`) multi-model tenant reference — only a single configured `tenant_model` class is supported.
- `spatie/laravel-medialibrary` or any third-party media management for attachments.
- Any pruning/retention command for old soft-deleted `InboundEmail` records.
- Automatic marking of `Processing`/`Processed` by the package — these remain entirely app-driven.
- Backward-compatible opt-out config flag for disabling persistence — it is unconditionally on in this fork.
- Changes to provider verification logic, `InboundMessage` DTO shape, or the job-dispatch contract.
- Full `spatie/package-skeleton-laravel` feature parity beyond what's listed (e.g. skeleton's specific `.editorconfig`, issue templates, or funding files) unless they fall out naturally from the restructuring work.
