# Single InboundEmail model instead of a separate Webhook + InboundEmail split

The reference implementation we're following (`trady`, a sibling Laravel app) splits this concern into two models: a generic `Webhook` (raw payload, source, processing status) and a separate `InboundEmail` (parsed fields, attachments via media library, `contactable`/`processable` morphs) linked implicitly through application code. We chose to combine both roles into one `InboundEmail` model instead: since this package is scoped to email specifically (not generic webhooks for arbitrary sources like Xero), there's no case where the raw-receipt row and the parsed-email row exist independently of each other, and keeping them combined avoids an unnecessary foreign key and two round trips for every webhook. The trade-off is that `InboundEmail` now carries both a raw `payload` column and a full set of normalized columns plus a status lifecycle — a wider model than either half of the trady split — which is deliberate given the narrower scope.
